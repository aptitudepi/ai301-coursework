# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis follows the repro evidence | The plan's diagnosis (cause statement) read against the repro-evidence block's observed behavior, artifacts, and control runs. | Pass only if the stated cause is consistent with every relevant observation and control in the repro evidence: the observed failure follows from the cause, and no control in the block rules that cause out or points to a different variable or component. Fail if the plan repeats a cause the evidence contradicts, ignores a control that isolates a different cause, or asserts a cause with no support in the evidence. | required |
| Change is bounded to the issue | The plan's scope statement, its in-scope/not-in-scope lines, and every proposed change (including "audit", "while in the area", and "also") read against the issue's reported behavior and the repro evidence. | Pass if each proposed change is necessary to fix the reproduced behavior, or is explicitly named as deferred/out of scope with a reason. Fail if the plan bundles unrelated work - a migration, redesign, new option, UI feature, retry framework, or drive-by refactor - that the issue did not ask for and the plan does not defer. | required |
| Approach is executable | The plan's files/areas, chosen mechanism, and order of work. | Pass if the plan names at least one concrete file, function, module, or code area and a specific change or mechanism, so a stranger could start without asking which layer or approach to use. Exact functions may be pinned during implementation only when the plan names the module/area and the mechanism. Fail if the plan defers the real choice to build time ("profile and optimize", "recover() somewhere", "upstream or vendored, whichever is easier", "look into caching"). | required |
| Test plan is decisive | The plan's test plan read against the repro evidence's steps and artifacts. | Pass if the plan names the repro command or steps to re-run and an observable outcome that distinguishes fixed from broken - an exact output, exit code, state, test assertion, or control comparison. Fail if the only test is "run the full test suite", "nothing else should break", "should feel fast", or another outcome no one could observe. | required |
| Plan comment engages the thread and repo conventions | The candidate plan comment read against the thread highlights and the repo-facts block (bug-report template asks, contribution policy, AI policy, maintainer direction). | Treat the candidate plan and plan comment as AI-assisted work by construction: every package is a candidate output of an AI-assisted planning task, so an AI-use disclosure requirement applies to the comment even when the comment never mentions AI. Pass if the comment engages explicit maintainer direction or prior work in the thread (a named culprit, a settled option, an open PR, a requested test) when such direction exists, or the thread has none and the comment does not contradict it; and if the comment follows every applicable stated convention, including AI-use disclosure when the policy requires naming the tool and extent. A policy that requires disclosure only in the pull request, or only human-authored comment wording, does not fail a plan comment that meets that stated scope. Fail if the comment ignores explicit maintainer direction, or omits a disclosure the repo's stated policy requires in issue comments. | required |
| Unknowns are stated honestly | The plan's risks, open questions, and deferrals. | Pass if the plan names at least one material risk or open question, or states that none were identified; deferrals name a reason. Fail if the plan hides a known unknown behind confident language. | preferred |

## Verdict rule

Accept only if every required check passes. Reject if any required check fails or is `unclear`; `unclear` counts as fail. Preferred checks never change the verdict.
